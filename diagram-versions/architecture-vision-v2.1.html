Agentic Delivery Platform: Architecture Vision

What gets built on Azure: one web app, the database and storage, and a pool of AI agents that grows and shrinks with the queue. The pool opens up one ticket to show the steps its agents follow, and how each agent talks to the AI models in Microsoft Foundry.

📦 Container Registry vs agent pool: why two boxes?The registry is a shelf; the pool is the workshop. The plugin (agents, skills, hooks, AGENTS.md) and the dev tools are packaged once into an agent image and kept in the registry. It does no work there. Each time the pool needs an agent, it pulls a copy of that image and runs it as a container. One stored image, many running copies. A new plugin version is a new image, so every agent gets the same tested version, and you can roll back.
🔁 How an agent works with Foundry (two-way)The agent runs in the pool; the model's “brain” is in Foundry. ① The agent sends a prompt: its task, the spec, the code and the tools it may use. ② The model replies with the next step: code to write or a tool to call. ③ The agent does it in its container (edits code, runs tests, calls MCP servers) and sends back the result. This repeats until the task is done. ④ Then the orchestrator moves the ticket to its next ADO state.
⚡ How do 15 tickets run at once?The task queue shows it: every agent task waits there as a message, and the pool starts one container per message, up to a set limit. The pool shows one ticket opened up (Ticket 1) and one collapsed (Ticket 2). Tickets 3 to 15 follow the same steps in their own containers. When the queue is empty, the pool shrinks to zero and costs nothing.
