Agentic Delivery Platform on Azure

The Azure setup that runs the Agentic Delivery Flow (v7) end to end: it picks up tickets, runs the agents in parallel, calls the right-sized model for each agent and tracks cost and quality. It runs under the team's own service identities, not anyone's personal account. Numbered arrows show how one ticket travels through the platform.

How tickets and approvals get in

Azure API ManagementOne secure entry point for webhooks from ServiceNow, Azure DevOps and GitHub. It checks each sender. The same instance is also the AI gateway (D).
Azure Functions · intake listenerTurns each event into a queue message. A timer also checks every few minutes, in case a webhook is missed.
0 · Intake Agent🧮 Small Sorts tickets, spots duplicates and links ServiceNow to ADO. It runs on the workbench (C).
Later: Teams chatContent authors give demands by chat (Azure Bot Service). Not in scope now.

B Orchestration

The scripted conductor: no AI cost

Azure Durable Functionswith the Durable Task Scheduler Runs one orchestration per story: fixed order, parallel steps, loop counts (max 3). It sets ADO states and keeps ServiceNow in step. At a 👤 gate it sleeps at no cost for hours or days until the approval event arrives.
Azure Service BusA queue of agent tasks. One session per story keeps that story's steps in order. Messages that keep failing go to a dead-letter queue → 👤 Needs Human.
WIP limit (setting)Caps how many stories are in Build at once. It protects model quotas, the shared Sitecore dev environment and reviewers' time.

C Agent runtime: the workbench

Where agents read, write and test code

Azure Container Apps jobs · agent runnerOne short-lived container per agent step. It starts when a task is queued and stops when the step is done. It scales out with the queue (KEDA) up to the WIP limit, and costs nothing when idle.
Runner imagein Azure Container Registry Claude Agent SDK + the team plugin (skills, hooks, AGENTS.md), Node 24, pnpm 11.5, Playwright browsers, .NET + Sitecore CLI. Each run gets a fresh checkout (this replaces git worktrees).
MCP connectorsIn the container: Playwright, Next.js DevTools, Storybook. Remote: Marketer, Docs, Vercel, Azure DevOps, ServiceNow, Figma.
Option: Foundry hosted agentsFor agents that only work with documents (PRD, review, spec, planner). Decide after the spike.

1Tickets and approvals arrive. ServiceNow, Azure DevOps and GitHub send webhooks to API Management, and a timer poll is the backup. The Intake Agent sorts new tickets into ADO stories.
2A story starts. When the backlog owner marks a story ready, the orchestrator starts one durable orchestration for it.
3One task per agent step. The orchestrator queues the step, and Container Apps starts a fresh container for it, with many in parallel up to the WIP limit.
4The agent thinks. It calls its pinned model size through the AI gateway, which enforces its token limits.
5The agent works. It clones the repo, builds and tests, and opens the PR as the GitHub App. It creates Sitecore items on dev and reads the Vercel preview, all through MCP or CLI.
6Results are saved. Story memory goes to Blob Storage, and the run record (tokens, cost, result) goes to the run ledger.
7People can see progress. The orchestrator sets the ADO state, adds comments, attaches the authoring guide and updates the ServiceNow ticket.
8Everything is measured. Every run and every model call sends traces, token use and cost to monitoring.
9Gates. At a 👤 gate the orchestrator sleeps until a person approves in ADO or GitHub. That approval arrives as an event (step 1) and wakes the story.

Key questions answered

⚖️ 15 tickets at once: do we need a load balancer?

No classic load balancer is needed for the agents. A load balancer spreads web traffic across servers that are already running. Agent work is different: each ticket is a long job. The standard pattern is a queue plus auto-scaling workers: tickets wait safely in the queue, and Azure starts more containers as the queue grows.

What really limits parallel work: the model's token quota, which the AI gateway spreads across deployments; the one shared Sitecore dev environment; and how many PRs people can review. The WIP limit is tuned to these.

A load balancer (Front Door or Application Gateway) only becomes relevant if a web app is added later, such as an agent control-centre.

🧮 Right-sized models and cost control

  • Large for judgement on small inputs (PRD review, task planning, contract, blueprint). Mid for code, tests, documents and content (most agents). Small for routine work (intake, PR text, bugs, deploy, performance, weekly report). No model for scripts.
  • Pinned per agent in configuration and changed only after evals pass. The model router suits general chat traffic, not a pipeline that needs predictable output.
  • Step-up on retry: the third round of a loop may use the next size up.
  • Spending brakes: the AI gateway applies a per-agent token-per-minute limit and monthly quota; Azure budgets alert at 80%. Prompt caching cuts the cost of repeated context such as AGENTS.md and skills.
  • All model spend goes on the platform's Azure subscription, not on any developer's Claude or Copilot seat.

🪪 Running without anyone's personal account

  • Agents and Azure services: managed identities and Entra Agent ID. No passwords to leak.
  • GitHub: a GitHub App. PRs show the bot as author, and its access is limited to this repo.
  • Azure DevOps: a service principal or managed identity.
  • ServiceNow: an integration user with only the rights it needs.
  • Sitecore: automation client credentials per environment.
  • Vercel: a team token. Its MCP uses a personal browser sign-in today, so this needs checking.
  • All secrets are in Key Vault, so when a person leaves, nothing breaks.

📊 Agent performance: what we measure

  • Flow: lead time from ready to PR and from ready to done; how long tickets wait at each gate.
  • Quality: first-pass success per agent; loop rounds per step; 👤 Needs Human escalations; defects found at preview versus after merge.
  • Cost: cost per ticket, per agent and per model size; tokens per step.
  • Health: failed runs, queue length, stuck stories, throttling (429) from the gateway.
  • Evals: pass rate on the set of past stories, tracked per release of the plugin.

👥 Do we need a PM or Scrum Master?

For the agents: no Scrum Master. Agents don't need sprints or stand-ups. They pull the next ready story from a prioritised queue (Kanban-style), with the WIP limit as the brake.

But two human roles are needed: a backlog owner (priority and "ready for agents" can't be delegated to an agent) and a platform owner (budgets, evals, model choices, incidents).

Building the platform is a real project, with a backlog, sprints, a PM and stakeholders, and it shouldn't be built quietly in the basement. Agents can help with backlog hygiene and the weekly cost report, from rules people set.

🚫 Deliberately not in the first version

  • No custom web app: people work in ADO, GitHub and Azure dashboards, which they already use.
  • No load balancer, no Kubernetes (AKS): Container Apps jobs scale on their own.
  • No vector database: app memory is in the repo. Azure AI Search over past fixes can come later.
  • No GitHub Actions for agents: agents run on Azure. GitHub keeps only the code, PRs and the existing checks.

Rules this platform keeps
  • No step uses a person's account, licence or token budget.
  • Every model call goes through the AI gateway, so limits and cost tracking always apply.
  • Scripts do the mechanics; AI is used only where judgement is needed.
  • No agent merges or publishes without a person's approval.
  • Every change to a model, prompt or skill passes evals first.
