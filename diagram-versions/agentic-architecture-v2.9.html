Agentic Delivery Platform on Azure: Foundry-first

How the Agentic Delivery Flow (v8) runs live on Azure, with Microsoft Foundry at the centre. Foundry holds the AI models, runs every agent and governs them. Azure services around it react to tickets in seconds, report progress on the Azure DevOps story and the ServiceNow ticket people already use, and keep the platform secure. The numbers ① to ⑨ follow one ticket through the platform, and 🪪 shows how each agent proves who it is.

🛒 Foundry is the model shopA catalogue of AI models, including Claude Opus, Sonnet and Haiku. You deploy the ones you want under your own names, and they are paid for through the Azure subscription.
🏠 …the home where agents runFoundry Agent Service runs the agents. Each agent session gets its own sealed sandbox, so a coding agent can clone the repo, build and test without touching anything else.
🎛️ …and the control roomEvery agent gets its own identity, guardrails, token limits and a full trace of what it did. Evaluations re-test the agents before a model, prompt or skill change goes live.

Without Foundry the team would wire these pieces together itself. With Foundry, models and agent governance are in one place, and the other Azure services only handle events, monitoring and data.

One ticket in real time (timings are illustrative)

  1. 10:00Ticket arrives. Someone creates a ticket in ServiceNow or Azure DevOps. A webhook reaches API Management straight away. If a webhook is ever missed, the safety net finds the ticket within minutes and sends it into Event Grid.
  2. 2+2 sTwo runs start, one after the other. Event Grid routes the event, and the orchestrator starts a short Intake run: the Intake Agent sorts the ticket and creates or updates the ADO story. When the 👤 backlog owner marks the story ready, that change is a new event, and the orchestrator starts the delivery run (steps 1–21).
  3. 3+5 sAn agent starts. The orchestrator asks Foundry Agent Service to start the next agent in a fresh sandbox from the agent image. It caps how many agents run at once, so extra work waits its turn, and it retries a failed step before marking the ticket 👤 Needs Human.
  4. 4seconds to minutesThe agent thinks. Each call carries its 🪪 Agent ID token and the ticket label. The gateway checks them, applies the limits and forwards to the pinned model. The agent loops (ask, reply, act) until its task is done.
  5. 5The agent acts, using only the tools on its own list. Remote MCP tools reach outside systems (ADO comments, the GitHub PR, the Vercel preview). Inside its sandbox it uses git, pnpm and the Sitecore CLI, plus local MCP tools such as Playwright.
  6. 6Progress is saved. Story memory goes to Blob Storage. The orchestrator moves the ADO story to its next state.
  7. 7seconds after each stepStatus shows where people work. The ADO story moves to the v8 state for the stage, with the agent's comment. If the ticket came from ServiceNow, it moves Open → In progress → Resolved, and to On hold while the flow waits on someone outside the team.
  8. 8👤 Gates. The run sleeps at no cost until a person approves in ADO or GitHub. The approval is an event, so the run carries on within seconds.
  9. 9all the timeEverything is measured. Traces, evaluations and cost go to the control plane and Application Insights. Alerts fire if a ticket is stuck.

"Real time", three ways

⚡ Event-drivenNothing waits for a schedule. Webhooks and Event Grid start work within seconds, and approvals are events too. The timer only catches a missed webhook.
🏭 Production-readyReal Azure services, no personal accounts, secrets in Key Vault, a private network, guardrails and evaluations. Dev, test and prod are built the same way from code.
👀 Status where people workEach step updates the ADO story (state and an agent comment) and, for ServiceNow tickets, the original ticket. No extra status app to run or pay for.

Services we configure, and code we write

⚙️ API Management · an Azure serviceWe give it settings, not code, like the bindings and rules on a web server or a reverse proxy. For example: ServiceNow posts "ticket created", API Management checks the shared secret and the rate limit, then passes the event on.
⚙️ Event Grid · an Azure serviceA routing service, like a mail sorting room. For example: "ticket created" goes to the orchestrator, and "PR approved" wakes the run that is waiting for it. If delivery fails, it retries for up to 24 hours.
📝 Function App · our codeOne app that holds the orchestrator, the safety net and the scripted steps. They deploy together and share settings. This is the only box in the column that the team codes.
⚙️ Service Bus · an Azure service, optionalA queue service, like the ticket-number line at a service counter. For example: 20 agent jobs arrive, 5 start, 15 wait in line, and a job that fails 3 times moves to a "dead-letter" list. Add it if volume grows past what the orchestrator's own limits handle.

Microsoft Entra ID sits outside the resource group because it belongs to the whole organisation (the tenant). Everything inside the dashed box is created new for this platform, once per environment.

Before building more

🧪 Prove in a spike
  • Run one coding agent (7 · FE Agent, Mid model) as a Foundry hosted agent with the team's image. Check it can clone, build and test the monorepo.
  • Confirm the Claude Agent SDK is supported inside hosted agents. A news report lists it, but no Microsoft or Anthropic guide was found yet. Fallbacks: Microsoft Agent Framework with Claude models, or v1's Container Apps runner.
  • Check Claude model quota and region availability for the subscription.
  • Confirm Foundry guardrails (content filters, prompt shields) apply to the Claude deployments. If not, apply Azure AI Content Safety in the AI gateway instead.
  • Compare Durable Functions and Foundry workflows for a gate that waits several days.
  • Check how Event Grid reaches the Function App on a private network. Event Grid can't push to a private-only address, so either allow only Event Grid in, or deliver through a Storage queue.
  • Confirm Foundry hosted agents can run inside the virtual network.
  • Decide how many agents may run at once. Foundry session limits and the model quota set the ceiling.
  • Measure the cost of one real ticket, end to end.
❓ Open questions
  • Does On hold pause the SLA in the client's ServiceNow? Check with its admin before using it for 👤 Needs Human.
  • Can the client's ServiceNow instance send webhooks, or does it need the timer only?
  • The current address of the Sitecore Docs MCP server.
  • Which Azure region the platform should use (it decides model availability and data residency).
