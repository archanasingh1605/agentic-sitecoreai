Agentic Delivery Flow

How a user story moves from Azure DevOps to a deployed, tested Sitecore AI (XM Cloud) + Next.js component, and optionally to authored content. Each lane is a category of agents; numbers show the order of work. Coloured tags show which agentic concepts each step uses.

Version 4.2 · 25 Oct 2026 Draft for PM review Every agent runs as a subagent with its own context
📦 Packaged as one team plugin All agents, skills, hooks and connectors install together, so every developer runs the same version of this flow.

🎼 Orchestration: who runs the flow

Default: scripted. A scripted orchestrator runs the steps in a fixed order, starts parallel steps together, counts loop rounds (max 3) and pauses at human gates.

Phase by phase. Each phase starts from an event (the ▶ triggers in the Phase column), and progress is saved in story memory, so the flow can wait hours or days at a gate and resume.

AI orchestration where judgment is needed, marked 🤖: the Task Planner deciding the order of work, and the Contract Agent sending the plan back.

Azure DevOps state. The orchestrator sets the story's state as each stage starts (no AI cost). Agent-level detail is added as a comment on the story. Any loop that hits 3 rounds sets 👤 Needs Human.

🧠 Memory: what the flow remembers

  • App memory (shared, in the repo): project conventions in AGENTS.md, the blueprint, lessons learned. Applies to every developer and every story.
  • Story memory (one folder per story): PRD, design reference, spec, task list, contract, fix and bug lists, loop counts. How agents hand work over.
  • Developer memory (each developer): personal preferences in CLAUDE.md, git-ignored so it stays personal. Not used by the automated flow.

Rules that apply across the flow
  • Every loop runs at most 3 rounds, then escalates to a human with a summary.
  • An agent never reviews its own work.
  • The design reference (Figma or the chosen prototype) is the single source of truth for how the result should look.
  • Agents pass work to each other through story memory (PRD, spec, task list, contract, bug list).
  • SonarQube and CodeQL in GitHub remain the final gate on the PR.
Azure DevOps states, in order
New→ Requirements→ Design*→ 👤 Awaiting Design Pick*→ Finalizing Requirements→ In Development→ Quality Checks→ Preparing Authoring Guide→ Preview Testing→ 👤 Awaiting PR Approval→ Deployment in Progress→ Under QA Review→ Content Authoring*→ 👤 Awaiting Publish Approval*→ Done
At any time: 👤 Needs Human when a loop hits 3 rounds. Fix rounds return the story to In Development. *Only when that step is used.
Connectors used
  • Azure DevOps: read stories, log bugs
  • Figma: design reference when the story has a Figma URL
  • GitHub: commit, PR, merge
  • Sitecore AI (XM Cloud) dev: templates, renderings, items and serialization (BE Agent), and deploys
  • Sitecore Marketer MCP (official): test pages, content, Brand Kit and page checks. It can't create templates or renderings, so the BE Agent doesn't use it
  • Sitecore Docs MCP (official): Sitecore developer documentation for the blueprint, contract, code and authoring guide
  • Vercel: preview URLs and frontend deploys
  • Browser: testing the preview and dev pages
